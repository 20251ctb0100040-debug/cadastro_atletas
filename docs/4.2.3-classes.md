# 4.2.3 Modelagem de Classes

## 1. Dos substantivos às classes

As classes foram identificadas a partir dos substantivos presentes nos casos de uso da seção 4.2.2 e dos requisitos funcionais da seção 4.2.1. Foram consideradas as informações que o sistema precisa armazenar para realizar o cadastro dos atletas, organizar as modalidades, registrar as inscrições e disponibilizar os resultados.

Nem todo substantivo se transforma em classe. Informações que representam características de uma entidade tornam-se atributos, enquanto os atores que apenas utilizam o sistema não precisam necessariamente ser classes.

| Substantivo | De onde veio | Vira | Por quê |
|---|---|---|---|
| Atleta | RF01, RF02, RF03, RF04 e casos de uso | Classe **Atleta** | O sistema precisa armazenar e organizar os dados dos participantes. |
| Modalidade | RF07 e caso de uso Gerenciar Modalidades | Classe **Modalidade** | O sistema precisa manter as modalidades esportivas cadastradas. |
| Inscrição | RF10 e caso de uso Inscrever-se em Modalidades | Classe **Inscricao** | O sistema precisa registrar a participação dos atletas nas modalidades. |
| Resultado | RF12 e caso de uso Consultar Resultados | Classe **Resultado** | O sistema precisa disponibilizar os resultados dos jogos. |
| Regra | RF08 e caso de uso Definir Regras dos Jogos | Classe **Regra** | O sistema precisa armazenar as regras definidas pela Comissão Organizadora. |
| Nome e matrícula | Cadastro do atleta | Atributos de **Atleta** | São informações que identificam o participante. |
| Data da inscrição | Caso de uso Inscrever-se em Modalidades | Atributo de **Inscricao** | Representa quando o atleta realizou sua inscrição. |
| Administrador e Comissão Organizadora | Atores da seção 4.2.2 | Não viram classes neste modelo | Representam usuários externos que interagem com o sistema. |

Os campos específicos do cadastro, das regras e dos resultados ainda precisam ser confirmados com o cliente.

## 2. Classes

As classes representam as principais informações que o sistema precisa armazenar e as operações que podem ser realizadas sobre elas. Cada classe possui atributos e operações relacionados aos requisitos funcionais.

| Classe | Atributos | Operações | Veio de |
|---|---|---|---|
| **Atleta** | - idAtleta: int, - nome: String, - matricula: String | + cadastrar(): void, + editar(): void, + excluir(): void, + consultar(): void, + validarDados(): boolean, + salvar(): void | RF01, RF02, RF03, RF04, RF05 e RF06 |
| **Modalidade** | - idModalidade: int, - nome: String | + gerenciar(): void | RF07 |
| **Inscricao** | - idInscricao: int, - dataInscricao: Data, - status: String | + inscrever(): void, + acessarInformacoes(): void | RF10 e RF11 |
| **Resultado** | - idResultado: int, - classificacao: String | + consultar(): void | RF12 |
| **Regra** | - idRegra: int, - descricao: String | + definir(): void | RF08 |

Os atributos apresentados são uma proposta inicial de modelagem. A matrícula, a classificação e os demais campos deverão ser confirmados com o cliente antes da implementação.

## 3. Diagrama de Classes

**Figura 2 – Diagrama de Classes do Sistema de Cadastro de Atletas**

O diagrama apresenta as cinco classes principais do sistema: Atleta, Modalidade, Inscricao, Resultado e Regra. Cada classe possui seus atributos e operações, representando as informações armazenadas e as funcionalidades realizadas pelo sistema.

As associações representam as ligações entre as classes. Um atleta pode realizar várias inscrições, enquanto cada inscrição pertence a um único atleta. Uma modalidade pode possuir várias inscrições, e cada inscrição está relacionada a uma modalidade. Uma inscrição poderá possuir um resultado quando a participação do atleta tiver um resultado registrado.

A classe Regra representa as regras definidas pela Comissão Organizadora para as modalidades esportivas. A ligação entre essas classes deverá ser confirmada com o cliente.

![Diagrama de Classes](../diagramas/classes.png)

**Fonte:** Elaborado pelo autor (2026).

### Relacionamentos entre as classes

- **Atleta e Inscricao:** um atleta pode possuir nenhuma ou várias inscrições (0..*), mas cada inscrição pertence a exatamente um atleta (1).
- **Modalidade e Inscricao:** uma modalidade pode possuir nenhuma ou várias inscrições (0..*), mas cada inscrição pertence a exatamente uma modalidade (1).
- **Inscricao e Resultado:** uma inscrição pode ainda não possuir resultado ou possuir um resultado (0..1). Cada resultado pertence a uma inscrição (1).
- **Modalidade e Regra:** uma modalidade pode possuir regras associadas, conforme a organização definida pela Comissão Organizadora. A multiplicidade precisa ser confirmada.

Não foi utilizada herança porque as classes identificadas não apresentam uma relação de especialização que justifique esse tipo de ligação.

Também não foi utilizada composição ou agregação, pois ainda não existe informação suficiente para afirmar que uma classe depende da existência de outra ou que seus objetos são excluídos juntos.

## 4. Teste de Objetos

Um diagrama de classes representa a estrutura do sistema. Para verificar se os relacionamentos estão corretos, podemos utilizar uma situação hipotética envolvendo um atleta inscrito em uma modalidade.

A situação: a atleta Ana está cadastrada no sistema, realizou sua inscrição na modalidade Vôlei e possui um resultado registrado na competição.

**Figura 3 – Diagrama de Objetos do Sistema de Cadastro de Atletas**

![Diagrama de Objetos](../diagramas/objetos.png)

**Fonte:** Elaborado pelo autor (2026).

| Objeto | Classe | Valores |
|---|---|---|
| ana | Atleta | idAtleta = 1, nome = "Ana", matricula = "2026001" |
| volei | Modalidade | idModalidade = 1, nome = "Vôlei" |
| inscricao01 | Inscricao | idInscricao = 1, dataInscricao = "10/11/2026", status = "Confirmada" |
| resultado01 | Resultado | idResultado = 1, classificacao = "1º lugar" |
| regra01 | Regra | idRegra = 1, descricao = "Regras da modalidade" |

**Ligações entre os objetos:** ana e inscricao01, volei e inscricao01, inscricao01 e resultado01, volei e regra01.

### O que o teste confirma

- **Um atleta pode realizar várias inscrições.** A atleta Ana está relacionada a uma inscrição, mas poderá realizar outras inscrições em diferentes modalidades.
- **Uma modalidade pode possuir vários atletas inscritos.** A modalidade Vôlei poderá estar relacionada a várias inscrições.
- **Uma inscrição pertence a um atleta e a uma modalidade.** Isso permite identificar quem está participando e em qual modalidade.
- **Uma inscrição pode possuir um resultado.** O resultado fica relacionado à participação do atleta na modalidade.
- **Uma modalidade pode possuir regras.** As regras são definidas pela Comissão Organizadora.

O teste demonstra como as classes se relacionam em uma situação concreta. Caso novas informações sejam identificadas durante o desenvolvimento, os atributos e relacionamentos poderão ser ajustados.

## 5. Rastreabilidade com a Seção 4.2.2

A tabela de rastreabilidade relaciona as operações e os atributos das classes com os requisitos funcionais e os casos de uso definidos anteriormente.

| Operação ou atributo | Classe | De onde veio |
|---|---|---|
| cadastrar(), validarDados() | Atleta | RF01 e RF05, fluxo principal de Cadastrar Atleta |
| editar(), salvar() | Atleta | RF02, RF05 e RF06 |
| excluir() | Atleta | RF03 |
| consultar() | Atleta | RF04 |
| gerenciar() | Modalidade | RF07 |
| definir() | Regra | RF08 |
| visualizar os próprios dados | Atleta | RF09 |
| inscrever() | Inscricao | RF10 |
| acessarInformacoes() | Inscricao | RF11 |
| consultar() | Resultado | RF12 |
| nome, matricula | Atleta | Dados necessários para identificar o participante |
| dataInscricao, status | Inscricao | Registro da inscrição do atleta |

### Conferência da Rastreabilidade

**Toda operação tem origem.** As operações apresentadas nas classes estão relacionadas aos requisitos funcionais da seção 4.2.1 e aos casos de uso da seção 4.2.2.

**Todo requisito tem uma classe correspondente.** Os requisitos de cadastro, edição, exclusão e consulta estão representados na classe Atleta. O gerenciamento de modalidades está na classe Modalidade. As inscrições estão na classe Inscricao, os resultados na classe Resultado e as regras na classe Regra.

**O que a modelagem identificou.** A modelagem mostrou a necessidade de representar separadamente os atletas, as modalidades, as inscrições, os resultados e as regras dos jogos. A classe Inscricao é importante porque permite relacionar os atletas às modalidades em que participarão.

Dessa forma, a seção 4.2.3 complementa a modelagem de casos de uso, apresentando as informações que o sistema precisa armazenar e os relacionamentos entre elas.
